ChemExplorer

PubChem Chemical Space Explorer

Compare sampled chemical collections while keeping source evidence, molecular calculations, and model evaluation distinct.

Standalone public-data demonstration. The application runs locally in Python and Streamlit. This page is a technical case study, not the running application; no live computation or chemical dataset is hosted here.

The problem

Chemical collections have different definitions, sizes, overlap, and missing information. A useful comparison needs to preserve those differences rather than reduce them to an unexplained ranking.

The implementation

Joseph's demo project connects public API acquisition, reproducible sampling, molecular analysis, and structured reporting in a separate application. It demonstrates how scientific data become inspectable analytical outputs without using original research datasets or depending on the research systems described elsewhere in this portfolio.

  • Acquire and normalize: discover collections through PubChem classification, structure searches, and NCBI Entrez queries; retain definitions, candidate identifiers, exclusions, and retrieval status.
  • Compare molecular representations: use RDKit descriptors, Morgan fingerprints, scaffolds, and structural similarity to describe the sampled collections.
  • Evaluate separately: test eligible, independently defined group labels with nested cross-validation and baselines; report deposited GHS evidence as a separate descriptive stream.
  • Preserve traceability: export CSV tables, methods, deterministic result summaries, and versioned run manifests with run identifiers and CID-manifest checksums.

From source to report

The application boundary stays separate from this static portfolio.

  1. Public sourcesPubChem PUG REST / PUG View and NCBI Entrez
  2. Python workflowCollection definitions, seeded sampling, identity checks, and provenance
  3. Analysis modulesRDKit features, similarity, eligible group-label ML, and separate GHS coverage
  4. Streamlit and exportsInteractive inspection, CSV tables, methods, and a saved run manifest
Technology choices and boundaries

Streamlit provides the Python application interface; RDKit handles molecular representations; scikit-learn supports model evaluation. A local SQLite cache reduces repeat acquisition. The portfolio remains semantic HTML and CSS on GitHub Pages, which cannot execute the application. A shared live deployment would need coordinated request limits and a reviewed cache/storage policy, not only per-process throttling.

Validation and scientific limits

These are implementation practices described in the local project documentation, not independently verified performance claims.

  • Fixture-based pytest checks avoid live PubChem requests. No test-pass count or predictive-performance result is claimed here.
  • Saved candidate identifiers, sampling settings, versions, and exclusions support reproducibility; a new upstream query is not guaranteed to reproduce an earlier collection.
  • Structure-defined labels are blocked from supervised distinguishability analysis. Learned preprocessing and tuning remain inside training folds, with identical structures grouped to reduce leakage.
  • Deterministic, versioned templates summarize stored results; summaries are not language-model-generated evidence.

Interpretation boundary: sampled collections are not population-representative by default and do not establish real-world mixture co-occurrence. Group-label classification does not predict hazard, toxicity, exposure, or risk. Missing deposited GHS evidence does not mean a chemical is safe. No composite hazard score is calculated.

Demonstration availability

No public application URL has been verified. The supplied Nexus repository could not be accessed anonymously during integration, so a public source-code link is not advertised here.

The next publishing milestone is a reviewed, precomputed report from approved public inputs. Visitors could inspect and filter its stored results on Pages without executing Python. Live acquisition, model training, and arbitrary manifest uploads would remain outside that static demonstration.

Proposed private-to-public release boundary

A GitHub Actions build can execute approved code in the source repository and produce an explicitly allowlisted HTML/CSS/JavaScript report bundle. Only reviewed output would enter the public Pages deployment. Source code, caches, logs, credentials, original research data, and unapproved derived artifacts must stay out of that bundle. This publication pipeline has not been implemented; a build does not automatically sanitize its inputs or outputs.
